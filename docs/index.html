Microsatellite instability (MSI) detection Workflow

Introduction

This workflow detects microsatellite instability (MSI). It is written in WDL and run with sprocket on a Slurm + Apptainer backend. It uses two tool modules, MSIsensor-pro and bedtools, and three Apptainer images: one per tool plus a generic Python image for the other steps.

It runs MSIsensor-pro (tumor-only) on every BAM of a run directory, once the upstream pipeline (ADIVAR) has finished that run. Controls are skipped: BAMs whose name starts with TN or TPH.

Before that, msisensor-pro scan lists every microsatellite of the genome (once: the result is cached, or given as pro_list). bedtools then intersects this list with the panel BED, so that only the microsatellites inside the panel regions are analysed, and with the ROI BED, which names the classic MSI markers (BAT25, BAT26, NR21...) among them.

In cron mode, the pipeline compares two lockers: ADIVAR's (JSON, status 3 = finished) and the MSI locker (text, one run per line = already analysed). A run finished by ADIVAR and not yet in the MSI locker is analysed, then added to it.

As a safeguard, the cron only launches when exactly one run differs between the two lockers: with more, it stops with an error and analyses nothing.

For the picked run, the pipeline reads a single field of its SampleSheet.csv: the Experiment Name, which gives the BAM folder to analyse.

Before the first cron launch

So that the cron does not analyse every past run, fill the MSI locker with the runs ADIVAR has already finished.

# same lockers as LOCKER_ADIVAR / LOCKER_MSI of BASH.sprocket.cron.sh
L=/path/to/locker
./companion-scripts/make_msi_locker.py --locker-adivar $L/adivar-testNS.json --locker-msi $L/msi-sensor.locker.txt --dry-run   # prints the runs to add
./companion-scripts/make_msi_locker.py --locker-adivar $L/adivar-testNS.json --locker-msi $L/msi-sensor.locker.txt

Configuration

Edit these files by hand at install:

  • params/template.json: references and thresholds of each run
  • params/install.json: Apptainer images and Python scripts
  • backends.conf/sprocket.prod.toml: sprocket and Slurm settings
  • BASH.sprocket.cron.sh: folders and lockers of the cron mode
  • finally, edit the crontab, to launch BASH.sprocket.cron.sh

params/template.json: (copied by pre_process for each run; run and samples stay empty, filled per run). Define a FASTA genome (genome), a BED of your panel (bed_panel) and a BED of the ROI markers (bed_roi), the marker name in the 4th column (custom naming), e.g. ROI.hg19.bed:

chr2	47641530	47641644	BAT26	0	+
chr2	95849332	95849414	NR24	0	+
chr4	55598161	55598266	BAT25	0	+
chr11	102193479	102193564	NR27	0	+
chr11	125490736	125490816	NR22	0	+
chr13	31722591	31722667	HT17	0	+
chr14	23652317	23652397	NR21	0	+

Set the workflow's thresholds in the same file, under msi_detection.params (current values in params/template.json, each key described in Inputs).

params/install.json: paths of the Apptainer images and Python scripts the WDL workflow uses (details below).

Quick start

cd /path/to/pipeline-jp
./BASH.sprocket.cron.sh                       # cron mode: pre_process picks the run left to analyse, then runs it
./companion-scripts/BASH.sprocket.batch.sh CONFIG_DIR VIZ WORK   # batch mode: every params JSON of CONFIG_DIR

The batch mode runs sprocket in the current shell (hours for a whole group): launch it in screen / tmux, or a lost terminal / SSH session stops it. Not needed for the cron mode (no terminal).

BASH.sprocket.cron.sh (cron) first runs msi_detection_pre_p.py three times, each container mounting only what that step reads:

  1. --print-run (job msi-pick_run; the two lockers): prints the run finished by ADIVAR and not yet in the MSI locker;
  2. --print-experiment (job msi-experiment; + that run's $RUNS_DIR/<run>/SampleSheet.csv): prints the Experiment Name of its [Header], the name of its BAM folder;
  3. without option (job msi-pre_process; + that run's $BAMS_DIR/<Experiment Name>/, the MSI locker and $WORK/config/ writable): writes its params JSON in $WORK/config/ and adds the run to the locker.

Neither the whole $RUNS_DIR nor the whole $BAMS_DIR is mounted. A sample sheet without Experiment Name or a missing BAM folder stops the script before the run is locked (retried at the next launch). Then both scripts, for each params JSON:

  1. sets the destinations, hardcoded in the script (not in the params): VIZ (reports folder) and WORK (sprocket's runs), created if needed;
  2. runs sprocket run -s -c $SPROCKET_CONFIG (backends.conf/sprocket.prod.toml) in $WORK/sprocket/runs/msi_detection/<timestamp>/, one folder per task;
  3. runs msi_detection_post_p.py index as a Slurm job (srun, in python-3.12.sif): copies the run's viz/runs/<run_id>/ into $VIZ/runs/ and rebuilds the dashboard from every $VIZ/runs/*/ (index_msi_run.js, index_msi_sample.js; the two .html are written once, only rewritten if their template changes).

The workflow itself never writes outside its tasks: the dashboard covers every run, a state that changes with each run, so it is built after the run (index), not by a task (a task reading the current reports would not be reproducible nor cacheable). index can be re-run at any time, e.g. after deleting a run folder. Everything else stays in sprocket's run folder (paths in its outputs.json), every task keeping its work/ folder (~300 MB per run).

Batch mode: params JSON and TSV export

The params JSON of a batch come from companion-scripts/make_configs.py: given a group folder of BAM folders (one per run: input/colon-msi, input/foie-mss...) and run names, on the command line and/or in a text file, it writes <run>_params.json (copy of params/template.json, run = <group folder>/<run>) in --output-dir (required: the launcher's OUTPUT_DIR). The group folder picks the run, the same run name being in several groups.

The runs file has one line per run, or per run + sample ID to analyse only some samples (columns separated by tabs or spaces, # comments allowed):

Run154_Juno                  # every BAM of the run (but the controls)
Run171_Juno  C22D03556T      # only these samples of Run171_Juno
Run171_Juno  C22D03587T

The sample IDs of a run go to "msi_detection.inputs".samples: ta01_find_bams then only keeps the BAMs whose name contains one of them (every library). A run without BAM, or with a sample ID matching no BAM of the run (checked before the workflow), gets no params JSON: its lines are written in <output-dir>/failed-runs.txt (same format as the runs file, for a rerun; removed when no run fails) and the script exits 1, the other runs being written.

After the batch, companion-scripts/export_tsv.py writes the results of its reports folder as a TSV, one line per sample: results_msi_<date>.tsv (date YYYY-MM-DD_HH-MM-SS: each export is a new file), in the launcher's OUTPUT_DIR (required), in the reports folder with the python script alone (--output-dir). It recomputes nothing: it reads the dashboard data (index_msi_sample.js, then each sample's runs/<run_id>/<sample>_index_sample.js), so the table matches the dashboard. Columns: run_id, sample_name, call, consensus_roi, consensus_total, pct_region_unstable; per library <lib>_unstable_region_count, <lib>_unstable_roi_count; per ROI marker <marker> (its site status, the same for every library), then <lib>_<marker>_pro_p and <lib>_<marker>_cov for each library (no mean). Empty cell: no value.

Both run through a launcher, like the other python steps: a Slurm job (srun, jobs msi-make_configs / msi-export_tsv) in python-3.12.sif (python3 -I), mounting the code read-only, what the script reads (read-only) and the folder it writes:

S=/path/to/data
./companion-scripts/BASH.make_configs.sh $S/input/foie-mss $S/config/runs-test.txt $S/config/config-test
./companion-scripts/BASH.sprocket.batch.sh $S/config/config-test $S/output/config-test/viz $S/output/config-test/work
./companion-scripts/BASH.export_tsv.sh $S/output/config-test/viz $S/output/config-test      # -> $S/output/config-test/results_msi_<date>.tsv

The python scripts can also be run directly on the host (only the standard library): make_configs.py BAMS_DIR [RUN ...] [--runs-file TXT] --output-dir DIR, export_tsv.py --viz VIZ_DIR [--output-dir DIR | --output TSV].

Run by hand, with a params JSON written by pre_process (or a filled copy of params/template.json):

sprocket run -s -c backends.conf/sprocket.prod.toml msi_detection-0.1.0.wdl @params/install.json @$WORK/config/<date>-<run>-<Experiment Name>.json

The python steps of the workflow are subcommands of two self-contained scripts (a WDL task gets its script alone): main-scripts/msi_detection_main_p.py (msi_main_helper: list-to-bed, mark-list, the reference list) and main-scripts/msi_detection_report_p.py (msi_report_helper: report). They are kept apart because sprocket's call cache keys on each task's input files: editing the report must not invalidate the list steps, whose outputs are whole-genome lists (~100 MB each). main-scripts/msi_detection_post_p.py only holds index, run after the workflow by the BASH scripts; it imports the page code (CSS, <head>, .js writer) of msi_detection_report_p.py, next to it in main-scripts/.

The genome, panel and ROI must use the same build as the BAMs (e.g. GRCh37 + ROI.hg19.bed).
